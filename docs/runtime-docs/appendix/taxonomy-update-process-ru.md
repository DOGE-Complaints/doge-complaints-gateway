# Регулярное обновление таксономии меток — как это устроено и что делать руками

> Документ описывает **фактически существующий** процесс (метод `.cursor/rules/analysis.mdc` — всё по коду, пути указаны). Это «оглавление процесса»: детали телеметрии и бэкфилла живут в соседних appendix-доках, сюда они вынесены ссылками (раздел 13), чтобы не дублировать.

## Короткий смысл за один абзац
«Таксономия» — это набор **меток**, которыми помечаются issue на борде. Система **не обновляет таксономию сама**: она лишь непрерывно применяет *текущий* справочник меток к новым issue. Расширение/правка самого справочника — это **ручной цикл**, который запускает человек, когда видит, что появились новые типы обращений без подходящей метки. Сигнал к запуску цикла приходит автоматически (телеметрия «у метки нет перевода»), но дальше всё делают руками — либо пошагово (разделы 5–10), либо через **meta-script в Cursor** (раздел 3): посмотреть → решить → поправить код → раскатить → пере-проложить старые issue → проверить → сказать фронту.

## 0. Оператору простыми словами: что у вас сейчас и что делать дальше

### Вы накатили миграции — что это дало

В Supabase появились:
- таблица **`label_translation_misses`** — журнал «фронт не нашёл перевод для метки X на языке Y»;
- вьюха **`label_translation_misses_ranked`** — тот же журнал, удобно отсортированный для глаз.

Пока таблица **пустая или почти пустая — это нормально**, если в живом SPA ещё никто не ходил с «пропущенными» переводами (см. ниже).

### Taxonomy_builder — коротко

**Частично да, но с важными уточнениями.**

| Ваше ожидание | Как на самом деле |
|---------------|-------------------|
| «Периодически запускаю `@Taxonomy_builder.plan.md`» | **Да.** Только **вручную**, когда решили разобрать накопившиеся misses. Не по cron, не само. |
| «Он собирает новые лейблы» | **Да (TC1–TC2):** читает таблицу `label_translation_misses` и делает черновик решений. |
| «И они появляются как локализация во фронте» | **Только после ваших шагов:** TC3 (ответы на спорные ключи) → TC4–TC5 (правки **в коде репозитория**) → **деплой** gateway и spa. Cursor **не выкатывает** прод сам. |
| «Весь процесс целиком автоматом» | **Нет.** Вы участвуете в TC3 (решения), TC6b (разрешение на бэкфилл), ревью diff, коммит, деплой. |

**Что меняется в коде (не путать):**

1. **`spa-app/src/i18n/dictionaries.js`** — человекочитаемые подписи меток (et/ru/en). Это то, что видит пользователь вместо `Road Safety` / `infrastructure`.
2. **`doge-complaints-gateway/.../extraction_policy.py`** — только если новый **канонический токен от GPT** нужно смаппить на одну из 4 меток борда (`infrastructure`, `safety`, …). Без этого шага бэк и так подставит дефолт `infrastructure`, но «не туда».
3. **`reproject_issue_i18n.py`** — опционально, чтобы **старые** issue в БД получили новые метки после смены маппинга (только после вашего «go»).

**Итого одной фразой:** Taxonomy_builder — это **помощник оператора в Cursor**, который выгружает журнал из БД, предлагает черновик «что с каждым ключом сделать», по вашим ответам **правит файлы в git**, гоняет тесты. Живой сайт обновится только после вашего обычного деплоя.

### Что ещё нужно на фронте (важно — verified по коду)

**Приёмник на бэке есть** (`POST /telemetry/label-misses`). **Отправитель на SPA пока не подключён.**

Сейчас во `spa-app` при отсутствии перевода метка показывается через `humanize` (`labelDisplay.js` → `formatLabelKey`), но **запрос на бэк не уходит** — в `spa-app/src` нет вызова `/telemetry/label-misses` (gap **GL-5** в `spa-app/docs/analysis/localization-target-and-gap-analysis-2026-06-15.md`).

**Практический смысл для вас:**
- таблицу можно проверить SQL-запросом — она готова;
- **реальные пользовательские misses начнут копиться только после доработки SPA** (отдельная фронтовая задача: при humanize-fallback слать `{ label_key, locale }` на gateway);
- до этого можно **вручную** проверить цепочку тестовым POST (см. [`label-translation-misses-operator-ru.md`](./label-translation-misses-operator-ru.md)) или запускать taxonomy-цикл по тем ключам, которые вы и так видите на борде без перевода.

### Ваш рабочий чеклист «что делать сейчас»

1. **Убедиться, что таблица живая** (Supabase SQL Editor):
   ```sql
   select * from label_translation_misses_ranked limit 20;
   ```
2. **Доработать фронт** (или поставить в очередь spa): при показе метки без перевода — `POST /telemetry/label-misses`. Без этого журнал сам не наполнится от реального трафика.
3. **Погонять систему глазами:** открыть борд, найти метку без перевода в словаре — убедиться, что humanize работает; после пункта 2 — что строка появилась в таблице.
4. **Когда в таблице есть осмысленные строки** (или вы вручную накидали тестовые) — **запустить цикл в Cursor:**
   ```text
   @.cursor/plans/Taxonomy_builder.plan.md
   @doge-complaints-gateway/docs/runtime-docs/appendix/taxonomy-update-process-ru.md
   Taxonomy cycle TC0–TC7. cycle_id=YYYYMMDD. Claims из кода.
   ```
5. **Пройти ворота с агентом:** ответить на вопросы по спорным ключам (TC3), одобрить diff кода, сказать «go» на бэкфилл если нужен (TC6b), закоммитить и **задеплоить** gateway + spa.
6. **Повторять пункт 4 периодически** (раз в N недель / когда `miss_count` вырос) — не каждый день и не автоматически.

### Три «слоя» меток — чтобы не путаться

```
GPT прислал токен "sidewalk"
        ↓
Бэк (extraction_policy) → одна из 4 меток борда, напр. "infrastructure"
        ↓
Фронт (dictionaries.js) → "Infrastruktuur" / "Инфраструктура" / "Infrastructure"
```

Телеметрия пишет в таблицу **ключ, который фронт пытался перевести** (часто это уже `infrastructure`, `bureaucracy` и т.д. из payload issue). Taxonomy_builder по этому журналу решает: **добавить перевод в словарь** (частый случай) или **ещё и поправить маппинг на бэке** (если пришёл совсем новый канонический токен).

## 1. Три понятия, которые важно не путать

1. **Канонические метки от GPT** — свободные текстовые токены, которые приходят на вход вместе с историей (например `roads`, `broken_infrastructure`, `housing`). Их словарь не ограничен — GPT может прислать почти что угодно.
2. **Губернируемый набор меток борда** — закрытый список из **4 меток**, которые реально показываются и фильтруются на борде: `waste`, `district`, `infrastructure`, `safety`.
   → `src/core/projection/enums.py:22-28` (`DOGEIssueLabel`).
3. **Таблица соответствия** «канонический токен → метка борда» + правило по умолчанию. Именно она превращает свободные GPT-токены в одну из 4 меток.
   → `src/core/projection/extraction_policy.py:56-94` (`_CANONICAL_TO_SPA_LABEL`, `spa_labels_from_canonical`). Если токен неизвестен — метка по умолчанию **`infrastructure`**; если у кластера вообще нет меток — тоже `infrastructure`.

Отдельно существует **словарь переводов меток на фронте** (`spa-app/src/i18n/`, `AVAILABLE_LABELS` = 10 значений). Он **не совпадает** с бэкендом (4) — это осознанный текущий разрыв, который выравнивается вручную (раздел 10).

## 2. Общая картина цикла (7 фаз)

```
[АВТО]    Фаза 1. Сбор сигналов      — фронт шлёт «нет перевода метки» → копится в БД
   │
[РУЧНОЕ]  Фаза 2. Ревью оператором    — смотрим, что накопилось
[РУЧНОЕ]  Фаза 3. Решение             — что делать с каждым новым ключом
[РУЧНОЕ]  Фаза 4. Правка кода         — enum меток + таблица соответствия (+ перевод на фронте)
[РУЧНОЕ]  Фаза 5. Миграция/бэкфилл    — пере-проложить уже сохранённые issue
[РУЧНОЕ]  Фаза 6. Проверка/гейты      — тесты, /ready, ручной просмотр
[РУЧНОЕ]  Фаза 7. Коммуникация фронту — синхронизация словарей и контракт-доков
```

**Ускоренный путь:** фазы 2–7 можно пройти через meta-script TC0–TC7 (раздел 3) — те же шаги, но выгрузка, классификация и патчи кода делегируются CLI-скриптам; продуктовые ворота (решения, go на бэкфилл) остаются за человеком.

Фоном, независимо от цикла: кластеризационный cron каждые `CLUSTER_CRON_INTERVAL_S` применяет **текущую** таблицу соответствия к новым кластерам (`process_all_pending()` → проекция). Cron таксономию **не меняет** — он её только применяет. → `src/core/scheduler/cluster_cron.py:40-64`, `src/core/config/schema.py:57-58,210-216`.

## 3. Автоматизация цикла — как запускать и чего ждать

> После внедрения GW-L10N-03 для фаз **2–7** есть **meta-script** в Cursor: он не заменяет продуктовые решения, но снимает рутину — выгрузка телеметрии, черновик решений, патчи кода, dry-run бэкфилла, прогон тестов. SSOT скрипта: [`.cursor/plans/Taxonomy_builder.plan.md`](../../../../.cursor/plans/Taxonomy_builder.plan.md). Схема manifest: [`taxonomy-decisions-schema.md`](./taxonomy-decisions-schema.md). Layout артефактов: [`taxonomy-cycles/README.md`](../../tasks/run-reports/taxonomy-cycles/README.md).

### 3.1 Что автоматизировано, а что — нет

| Что | Кто делает |
|-----|------------|
| Сбор телеметрии «нет перевода» (фаза 1) | **Авто на бэке**; **отправка с SPA — ещё TODO** (см. §0, §4) |
| Запуск цикла обновления таксономии | **Только вручную** — нет cron, нет порога «само стартануло» |
| Выгрузка накопленных misses из БД | **Скрипт** `taxonomy_fetch_misses.py` (TC1) |
| Черновик «что делать с каждым ключом» | **Скрипт** `taxonomy_classify_candidates.py` (TC2) + эвристики |
| Решение по спорным ключам (вариант а/б/в/г) | **Человек** — интервью в чате (TC3) |
| Правка `extraction_policy.py` / `enums.py` | **Скрипт** `taxonomy_apply_gateway.py` (TC4) — по финальному manifest |
| Правка `spa-app` словарей | **Скрипт** `taxonomy_apply_spa_i18n.py` (TC5) |
| Бэкфилл старых issue | **Скрипт** `reproject_issue_i18n.py`; **запись** — только после вашего «go» (TC6b) |
| Тесты и статус в bullrun | **Скрипт/агент** (TC7) + ваша spot-check |

**Главное:** автоматизация **не меняет таксономию сама по себе**. Она помогает пройти уже описанный ручной цикл (разделы 4–10): быстрее собрать данные, оформить решения в одном файле и применить их к коду без копипасты.

### 3.2 Как запустить сессию

**Предусловия:** телеметрия работает (раздел 4); в `doge-complaints-gateway/.env` настроен доступ к БД (Supabase `SUPABASE_URL` + `SUPABASE_SERVICE_ROLE` или sqlite `DATABASE_URL` для локальной разработки).

**Шаг 0 — проверка, что всё на месте** (из корня monorepo `DOGEstonia/`):

```bash
python3 docs/methodology/Zeya888-builder-queue/cli/builder_resolve_queue.py --project taxonomy --verify
```

Ожидаемый ответ: `ok taxonomy verify (7 paths)`. При `FAIL missing files` — стоп, чините окружение до запуска цикла.

**Шаг 1 — открыть builder в Cursor.** В чате:

```text
@.cursor/plans/Taxonomy_builder.plan.md
@doge-complaints-gateway/docs/runtime-docs/appendix/taxonomy-update-process-ru.md
Taxonomy cycle TC0–TC7. cycle_id=YYYYMMDD. Claims из кода.
```

`cycle_id` — дата цикла в формате `YYYYMMDD` (например `20260529`). Она же попадёт в имя папки артефактов и в `run_mode=taxonomy_cycle_20260529`.

**Шаг 2 — Execute plan / Build.** Агент идёт сверху вниз: TC0 → TC7. Вы можете остановить сессию после TC3 (если нужно обдумать решения) и продолжить позже с тем же `cycle_id` и уже отредактированным `taxonomy-decisions.yaml`.

### 3.4 Что делает каждый скрипт (простыми словами)

**`taxonomy_fetch_misses.py` (TC1)**  
Читает ту же таблицу, что и операторская вьюха `label_translation_misses_ranked`: для каждой пары `(label_key, locale)` — `miss_count` и `last_seen_at`. Источник: Supabase REST (если в `.env` есть креды) или локальный sqlite. Пишет файл `misses-ranked.json` с полями `fetched_at` (когда сняли снимок) и `rows` (массив строк). В терминал: `Wrote N rows → <путь>`.

**`taxonomy_classify_candidates.py` (TC2)**  
Берёт `misses-ranked.json` и **живой снимок кода** — импортирует `DOGEIssueLabel` и `_CANONICAL_TO_SPA_LABEL`, списки не захардкожены в скрипте. Для каждого ключа применяет правила:

- `miss_count < 3` **или** ключ не проходит шаблон `^[a-z][a-z0-9_]{1,48}$` → `ignore` (вариант «г»);
- ключ уже есть в таблице соответствия **или** совпадает с одной из 4 меток борда → `translate_only` (вариант «в») — на бэке ничего менять не нужно, только перевод на фронте;
- иначе → `pending` — скрипт **не угадывает** map vs new label; ждёт вас в TC3.

Результат: `taxonomy-decisions.yaml` — единый manifest решений на весь цикл. В терминал: `Wrote N decisions (M pending) → <путь>`.

**`taxonomy_apply_gateway.py` (TC4)**  
Читает **финальный** manifest. Для `map` — добавляет строку в `_CANONICAL_TO_SPA_LABEL` (идемпотентно: повторный прогон не дублирует). Для `new_board_label` — только если в YAML явно `new_board_label: true`: добавляет член в `DOGEIssueLabel` и маппинг; без флага скрипт **откажется** (защита от случайной новой метки борда). `ignore`, `translate_only`, `pending` — пропускает. После записи — smoke-import `spa_labels_from_canonical`. В терминал: `Applied N gateway decision(s)` или `No gateway apply actions`.

**`taxonomy_apply_spa_i18n.py` (TC5)**  
Для `translate_only` и `new_board_label` дописывает ключи в `spa-app/src/i18n/dictionaries.js` (et/ru/en). Для новой board-метки — ещё `labelKeys.js` (`AVAILABLE_LABELS`). Если переводов нет в manifest — подставляет placeholder `TODO: product copy` (нужно заменить продуктовым текстом до релиза). Правит файлы **в соседнем проекте** `spa-app` из репозитория gateway.

**`reproject_issue_i18n.py` (TC6)**  
Без изменений от ручного процесса (раздел 8): `--dry-run` только печатает план; запись — отдельной командой после вашего подтверждения.

### 3.5 Логирование и артефакты — где смотреть следы работы

Автоматизация ведёт **два уровня** журналирования; их не путать:

**Уровень A — телеметрия (фаза 1, постоянно)**  
- **Где:** таблица `label_translation_misses` в БД; операторская вьюха `label_translation_misses_ranked`.  
- **Что:** анонимные счётчики «фронт не нашёл перевод для `label_key` в `locale`».  
- **Логи сервера:** при сбое записи — `label_miss_store_failed` в логах gateway; на пользователя это не влияет (`202 accepted:false`).  
- **Живёт вечно** (пока не почистите руками); цикл его не удаляет.

**Уровень B — артефакты одного прогона цикла (TC1–TC7)**  
Папка на диске (локально, обычно **не коммитится** без явной команды):

```
doge-complaints-gateway/docs/tasks/run-reports/taxonomy-cycles/cycle-<YYYYMMDD>/
```

| Файл | Когда появляется | Что внутри | Зачем оператору |
|------|------------------|------------|-----------------|
| `misses-ranked.json` | TC1 | Снимок БД на момент `fetched_at` | Аудит: «с чего начинали»; можно diff между циклами |
| `taxonomy-decisions.yaml` | TC2 → правится в TC3 | Все решения по ключам: `action`, `reason`, `auto: true/false` | **Главный след:** что решили и почему; SSOT для apply-скриптов |
| `reproject-dry-run.log` | TC6a | stdout dry-run бэкфилла | Проверить, сколько issue затронет запись |
| `run-summary-taxonomy-cycle-<DATE>.md` | TC7 | Итог сессии: тесты, статус, ссылки | Строка в bullrun Run Reports Registry |

**Stdout скриптов** — краткий итог в терминале Cursor (количество строк, pending, applied). Детали — в файлах выше, не в centralized log aggregator.

**Статус в реестре:** секция **Taxonomy Cycles** в [`bullrun-launch-index.md`](../../tasks/bullrun-launch-index.md) — ⚪ ready / 🟡 in_progress / 🟢 done для `taxonomy-<YYYYMMDD>`.

### 3.6 Где обязательно участие человека (ворота)

Скрипт **остановится или не сделает опасное** без вас:

1. **TC3 — интервью.** Все ключи с `action: pending` — выбор: `map` (б), `translate_only` (в), `ignore` (г), `new_board_label` (а). Новая метка борда — только с `new_board_label: true` и явным `target_label`.
2. **TC6b — бэкфилл.** После TC6a агент **должен остановиться**. Запись в БД — только после явного «go» / «пишем бэкфилл».
3. **TC7 — глазами.** `GET /node/issues?labels=<метка>` и согласование текста переводов (особенно если в manifest остались `TODO: product copy`).
4. **Коммиты.** Код gateway/spa — отдельные коммиты по стратегии builder; папку `cycle-*` в git — только по вашей команде.

### 3.7 Типичный сценарий от начала до конца

1. Видите рост misses во вьюхе (или по привычному порогу команды) → решаете запустить цикл.
2. Cursor + `cycle_id=YYYYMMDD` → TC0 verify зелёный.
3. TC1–TC2: появляются `misses-ranked.json` и черновик `taxonomy-decisions.yaml`. Смотрите YAML: сколько `ignore`, сколько `translate_only` (уже понятно — только фронт), сколько `pending`.
4. TC3: отвечаете на вопросы по `pending`; правите YAML (или просите агента обновить). `auto: false` у ручных решений.
5. TC4–TC5: меняются файлы в `doge-complaints-gateway` и `spa-app`. Review diff в PR-стиле.
6. TC6a: читаете `reproject-dry-run.log`. Если ок — говорите «go» → TC6b.

## 8. Фаза 5 — Миграция БД и бэкфилл `[РУЧНОЕ]`

Ключевой факт: проекция issue хранится как JSON-блоб `payload_json`, поэтому **смена справочника меток почти никогда не требует миграции БД** — меняется только код. Миграция нужна лишь если вы заводите *новую таблицу* (для меток борда это не нужно — они в enum).

Пошагово (бэкфилл):
1. Сначала «вхолостую» — посмотреть, что изменится, ничего не записывая:

   ```bash
   python3 scripts/reproject_issue_i18n.py --issue-id <id> # только конкретные
   ```
3. Скрипт идемпотентен (повторный прогон не портит данные) и пропускает issue без связей/проекции. Подробности и подводные камни — в отдельном доке: [`reproject-issue-i18n-backfill-ru.md`](./reproject-issue-i18n-backfill-ru.md).
