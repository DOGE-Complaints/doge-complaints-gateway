# План и анализ: чистая ветка `demo-ready-april-26`

## Цель

Подготовить отдельную Git-ветку `demo-ready-april-26`, в которой:
- **не будет legacy-кода** текущего репозитория (`app/`, `supabase/`, `db.sql`, `run.py`, и т.д.);
- останутся только материалы из `docs/` (включая requirements/analysis/solution architecture);
- будут сохранены только действительно необходимые служебные файлы репозитория (минимальный набор).

---

## Почему отдельная ветка — правильное решение

- отделяем “документарный demo контур” от текущего кода и техдолга;
- снижаем риск случайного смешивания новой архитектуры с legacy;
- удобно готовить презентационный/архитектурный baseline для пилота;
- сохраняем возможность вернуться к исходной ветке без потерь.

## Git-риски и как их избежать

- **Риск:** случайно удалить нужные документы.  
  **Контрмера:** перед удалением — инвентаризация `docs/**` и контрольный diff.

- **Риск:** оставить скрытые runtime файлы.  
  **Контрмера:** финальная проверка дерева и grep по ключевым legacy путям.

- **Риск:** потерять связь с исходной кодовой веткой.  
  **Контрмера:** явное описание в README + branch naming + optional tag.

## Решение по “что ещё брать из конфигов”

Для этой ветки почти ничего не нужно, кроме:
- `.gitignore`
- `LICENSE`
- обновлённый `README.md`

Остальные конфиги runtime/infra не несут ценности для docs-only демо и увеличивают шум.
